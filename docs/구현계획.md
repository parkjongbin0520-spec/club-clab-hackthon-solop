# 구현 계획

## 범위

이 문서는 요구사항 명세서 기준 **단일 동아리 활동 기록 관리 웹앱(MVP)**의 실제 구현 계획이다.
회원가입/로그인, 다중 동아리 목록/생성, 가입 조건 필터링 등 "동아리 찾기 플랫폼" 아이디어는
이번 MVP 범위에 포함하지 않는다 (사유는 맨 아래 "보류된 아이디어" 참고).

세션 하나 = 기능 하나 원칙([CLAUDE.md](../CLAUDE.md) "작업 방식")을 그대로 따르며,
아래 세션 순서와 [CLAUDE.md](../CLAUDE.md)의 "MVP 및 세션 계획" 섹션은 1:1로 대응한다.

## 파일 구조

- `index.html` — 화면 구조
- `style.css` — 스타일
- `app.js` — 기능 로직

## 데이터 모델

```
{ id, title, date, place, memberCount, memo, createdAt }
```

localStorage 키: `"activities"`

## 세션별 계획

### Session 1 — 로컬 환경 + 활동 등록

- VS Code Live Server로 `index.html` 실행 확인
- `index.html`: 등록 폼(활동명·날짜·장소·참여인원·메모·등록 버튼)
- `app.js`: `generateId()`, `saveActivity(activity)`, `handleSubmit(event)` — 폼 값 수집 후 저장, 저장 후 폼 초기화
- 완료 기준: 제출 시 devtools > Application > Local Storage의 `activities`에 항목이 추가됨
- 커밋: `활동등록: 입력 폼과 저장 기능 구현`

### Session 2 — 활동 목록 조회

- `app.js`: `loadActivities()`, `renderList()` — `createdAt` 기준 최신순 정렬
- 빈 목록: "아직 등록된 활동이 없어요" 문구 + 등록 버튼 강조
- 카드 UI: 활동명/날짜/장소 한 줄 요약, 클릭 시 참여인원·메모 펼침(아코디언)
- 커밋: `목록조회: 활동 리스트 렌더링 구현`

### Session 3 — 활동 삭제 + 입력값 검증

- `deleteActivity(id)` — `confirm()`으로 1차 확인 후 삭제, 목록 재렌더링
- `validate(activity)` — 활동명 필수, 날짜는 오늘 이후 불가, 참여인원은 1 이상 정수
- 검증 실패 시 폼 하단에 인라인 에러 메시지 표시
- 커밋: `삭제및검증: 삭제 확인 절차와 입력값 검증 추가`

### Session 4 — MVP 정리 + 배포

- README 체크리스트 갱신, 실행 화면 스크린샷 2장 이상 추가
- 같은 네트워크에서 다른 기기(폰) 접속 테스트: Live Server 네트워크 URL 또는 `npx serve -l tcp://0.0.0.0:3000` 후 PC 로컬 IP로 접속
- GitHub Pages 배포: 저장소 Settings → Pages → 브랜치 지정
- 커밋: `chore: MVP 정리 및 배포 준비`

### Session 5 이후 — 선택 기능 (우선순위 순)

1. 활동명·장소 키워드 검색 / 기간 필터 (목록 상단 인라인, 실시간 필터링)
2. 참여 인원 합계·평균 요약 카드
3. 월별 활동 횟수 통계 (숫자 요약 우선, 그래프는 여유 있을 때)
4. 데이터 JSON 내보내기/가져오기 (`Blob` + `<a download>`)
5. 활동 수정 (카드 클릭 시 등록 폼에 값 채우는 인라인 편집)
6. 반응형 레이아웃

각 항목 완료 시 README 체크박스와 CLAUDE.md "현재 진행 상황"을 갱신하고 커밋한다.

## 검증 방법 (세션 공통)

- devtools > Application > Local Storage에서 데이터 확인
- 새로고침 후 데이터 유지 여부 확인
- 콘솔 에러 없는지 확인

## 보류된 아이디어 (이번 MVP 범위 아님)

회원가입/로그인, 여러 동아리 목록/개설, 가입 조건(학년·전공·활동 시간) 설정 등
"동아리 찾기·가입 플랫폼" 컨셉은 이번 문서 범위에서 제외했다.

- **이유**: `localStorage`는 기기·브라우저별로 독립 저장되므로, 한 사용자가 만든 동아리 데이터가
  다른 사용자의 브라우저에는 보이지 않는다. 여러 사용자가 공유하는 목록/가입 흐름이 성립하려면
  서버·DB가 필요한데, 이는 과제 조건("서버·데이터베이스 도입 금지")과 충돌한다.
- 이 방향을 실제로 추진하려면 별도 프로젝트로 분리하고 Firebase/Supabase 등 백엔드 도입 여부부터
  다시 논의해야 한다.
